# Persistent drafts and menu publication

Local implementation slice, 12–13 October 2026. OTP remains deferred. Commands run only with trusted server-side principals; unverified onboarding cannot create a business, save private contacts to the database or publish. Isolated fictional businesses supply implementation evidence.

The first-branch preparation document maps into two separately versioned resources: a public branch-profile draft and a menu draft. Initial saves use expected version zero; later saves compare the version read by the editor. A stale editor must reload instead of overwriting newer work. An idempotency key replays the original committed response, even after later edits, and cannot be reused with a different body.

Branch-profile editing belongs to the owner. Authorized catalog editors can read it and edit/publish menus, but cannot change its customer contact. Profiles contain only the chosen business type and explicitly public branch settings. Registration names/phones/emails, authority, plans, billing and permissions are excluded.

Publication checks both draft versions, inserts an immutable snapshot and changes the branch's public route in one transaction. Draft edits never alter that route or live prices. Empty menus cannot launch. Catalog IDs stay bound to their business/branch and entity type; removed published items are archived rather than deleting order references. Financial and order snapshots remain unchanged.

The public reader returns a fixed projection of the active committed publication, with current item-availability overrides and an availability revision. Overrides survive publication so editing prices does not accidentally restock an item. Archived/unpublished/disabled routes are absent. Legacy unvalidated fixture snapshots are not automatically exposed through HTTP. The anonymous database role has no table access, editing authority or membership in the private workflow role.

The application uses parameterized queries and one checked-out connection per transaction, following [node-postgres query guidance](https://node-postgres.com/features/queries) and [transaction guidance](https://node-postgres.com/features/transactions). The public connection is explicitly configured and checked for its limited role; there is no automatic fallback to ambient database credentials. Private/session HTML and API responses remain outside the service-worker cache.

The customer page and its locally generated QR identify one published branch. They grant no visit, bill, identity or payment access. Customers browse the menu and ask staff to order while operational HTTP workflows remain unfinished. Protected editing endpoints fail closed until a trusted identity adapter is connected. A dedicated local fixture runner starts a private PostgreSQL cluster with TCP disabled; its database commands and restart tests are separate from ordinary onboarding.

The review QR uses a loopback URL and cannot be reached from a separate phone. Production requires an explicit `MENU_PUBLIC_ORIGIN` with HTTPS; the server ignores the caller's Host when building that link and rejects embedded credentials, path prefixes and loopback HTTP. Set the actual public origin and verify it on real phones before printing any live QR. The public reader uses `MENU_PUBLIC_DATABASE_URL` with a limited login inheriting `menu_public`; production TLS verification cannot be overridden by URL SSL parameters. The fixture-only socket configuration is rejected outside development. These configuration checks do not prove hosting, TLS, DNS or device reachability.

`catalog-mapping.ts` converts a validated preparation/export document into branch-profile and menu inputs. It preserves exact prices, translations and availability, canonicalizes IDs and adds no sample options. Its result excludes registration contacts and plan/entitlement assertions. The integrated fixture check persists that actual output and reads its publication through HTTP; the business stays Free and ordering stays disabled despite a Mini preparation preference.

Implementation files: `0005_menu_publication.sql`; server-only public connection/projection; four functional v2 HTTP operations (three preparation validators and public-menu GET); eight closed catalog/service/readiness boundaries; `/menu/[venueSlug]`; a locally generated QR. MenuMini now has an independent locked dependency tree instead of sharing the reference application's modules. The prepared business still uses page-memory/export recovery until trusted identity and authenticated onboarding are connected.

Acceptance: durable drafts after restart; two-business and role isolation; stale versions/retries/rollback; draft and publication separation; exact money/modifiers; immutable history and audit/outbox; overlapping saves/publications; safe customer HTTP responses and QR routing from a separate browser. These checks do not establish a production release or real-phone field acceptance.
