# Authorized payer access and transfer reports

15 October 2026. Local implementation and fictional acceptance. Real merchant OTP/access, bank actions, receiving-account onboarding, uploads and launch remain deferred. Extend the existing guest, cashier and ledger workflow; do not introduce a second payment truth.

A guest can order without becoming the table's payer. The guest screen displays a device code (last eight characters of its session UUID, uppercase). Cashier asks the intended payer to read that code, selects the matching joined and still-active session, and reviews authorization to share the combined bill. The code identifies a device for staff selection; it grants no access. API selection still uses the full server-listed UUID and verifies the visit/session relationship. A version check prevents authorizing from an obsolete bill review.

Cashier issues a one-hour grant capped by the guest session expiry. Reissuing for that guest/bill revokes prior grants without changing financial totals. Staff can explicitly revoke a current grant. Stable HMAC issuance reconstructs the same opaque token on exact retry; expired, revoked or superseded results report inactive. No plaintext token is stored in command results, audit or outbox. Private handoff uses an explicit code, never a URL. Issuance stays behind the existing closed merchant identity adapter.

The selected guest redeems the code with their own dining cookie and session-bound CSRF. A separate HttpOnly, SameSite Strict, host-only cookie binds subsequent reads and reports to the same guest and bill. Production requires Secure HTTPS. A token copied to another guest cannot authorize access. The limited guest database role has no direct table access or staff permissions. Entry commands clear ambient context, resolve both capabilities, serialize mutations with the branch, then recheck expiry/revocation. Leaving bill access revokes that grant and clears its cookie while retaining the guest's own-order session. Ending seating does not erase still-valid bill access or outstanding obligations.

The authorized shared view shows accepted bill charges and corrections, exact totals, table/seating context and the payer's own transfer reports. It excludes other diners' notes/instructions, session IDs, other payers' transfer references, cashier verification notes, staff identities and receipt history. Own reports use bounded keyset pagination. Oversized shared charge history fails explicitly rather than silently omitting charges. Verified active branch receiving destinations are available only to this authorized payer. Account details are displayed for independent use in the payer's banking application; no button or API initiates a bank transfer.

A report records an amount already sent, a receiving-account ID, the exact displayed destination fingerprint, a provider reference and an explicit already-sent acknowledgement. It never changes received or allocated funds. Partial and excess/late reports are allowed because money may already have been sent; zero/invalid amounts and unsupported receipt-asset inputs are rejected. When the balance is settled, the interface does not suggest making another transfer. Pending reports are not payment. Cashier still independently verifies credited funds, records the actual amount and explicitly allocates it using the existing atomic receipt/ledger commands.

New reports freeze the reviewed receiving destination. A changed destination/verification/link causes a conflict before submission; after submission an approval trigger rejects a changed destination, requiring supervised reconciliation rather than attributing funds to another account. The private cashier projection displays the original masked destination. A conservative case-insensitive duplicate guard rejects already pending/approved or recorded account/reference pairs; unique pending/approved-claim and canonical-receipt indexes plus receiving destination/reference advisory locks preserve this rule across branches. Existing histories conflicting with these new indexes must be reconciled before migration; this guard is not provider-specific reference canonicalization. Rejected reports can be corrected and resubmitted. At most one pending report per payer/bill and five new reports per session/hour are initial abuse guards, not commercial limits. An exact committed retry remains recoverable without consuming another allowance or creating evidence twice.

The browser rehearsal shares claims with the cashier view. It clearly marks account details and transfers fictional, uses memory only and resets on reload. Independent server/DB, real local HTTP, Postman, concurrency and restart checks verify actual capability and financial behavior separately. Supported reports now have encrypted interrupted-command recovery across full page reload; see [command-recovery-design.md](command-recovery-design.md). Production key lifecycle/delivery, log redaction, real devices, provider/reference procedures, receiving-account onboarding, private uploads and pilot acceptance remain gates.
