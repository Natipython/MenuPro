# Cashier bill settlement

15 October 2026. Extend the staff workflow with a private cashier worklist and bill settlement. OTP, real merchant access, guest pairing, receiving-account onboarding and external banking remain deferred. A fictional rehearsal and isolated PostgreSQL fixtures provide review without live financial activity.

The worklist includes all non-closed bills, including ended visits. Closed bills have a separate paginated history view. A short bill identifier, table label, seating status, date and exact amounts distinguish successive seatings at the same table. Bill detail exposes accepted charges, credits, receipt balances, pending claims and refund obligations only to staff with payment permission. Floor staff retain the narrower existing bill-balance read.

Cashier reviews requests before finalization, explicitly records counted cash/change or independently verified credited transfers, then explicitly allocates received funds to the receipt’s original visit bill. Cross-bill reassignment needs a separately reviewed procedure. A receipt alone leaves funds unapplied. Partial allocations retain an outstanding balance. Credits and refund approval/execution require manager permissions. Approval is not execution; execution records already-returned funds and never initiates a transfer. Pending claims/screenshots are never payment. An explicit acknowledgement is required for recording received funds, approving credited funds and recording actual refund execution.

Commands serialize business then branch, check current permissions and versions, use exact decimal strings, commit immutable facts/audit/outbox together and preserve the original response for exact retries after later changes. Supported cashier commands now save an encrypted IndexedDB journal before sending, restore the original key after reload and resolve it with current authority; see [command-recovery-design.md](command-recovery-design.md). Authenticated merchant browser acceptance and supervised reconciliation remain activation gates. A closure needs finalization and resolved service, outstanding balance, unapplied funds and refund reservations. Late real receipt/correction can reopen financial resolution. Subscription expiry does not prevent resolving existing obligations.

The API adds a bounded keyset bill worklist and private settlement detail. Detail rejects histories exceeding its explicit technical bound rather than silently omitting financial records; history pagination/export remains required before lifting that guard. Receiving accounts are active, ownership-verified and branch-linked; only a masked label is returned. No account creation or ownership verification bypass is added.

The browser rehearsal is clearly fictional and changes memory only. Server/DB tests independently verify pricing/receipt conservation, roles, cross-business access, stale versions, duplicate references, original-response retries, overlapping allocation/closure commands and restart durability. Authenticated HTTP, real phones/banks, account/reference normalization, fiscal receipts, uploads, reconciliation exports and pilot acceptance remain separate gates.
