# Staff-assisted dine-in service

13 October 2026. Continue preparation into table administration, visits, staff order entry, a durable service queue and serving. Real OTP and merchant sessions remain deferred. Private HTTP entry points use the existing closed identity adapter; fictional principals are supplied only in isolated in-process tests.

Owner creates or updates a table → assigned floor staff opens a staff-only visit → staff selects the committed menu and options → the server prices a submitted request → staff accepts while unpaid → preparation marks preparing/ready → floor staff records served. Only acceptance adds a bill charge. Serving does not record payment. Ending a visit requires service resolution but retains financial obligations. Repeated rounds share the visit's bill.

Staff-only visits return no guest/payer capability. The stored pairing hash has no issued token; guest pairing and a secure repeatable token-issuance policy remain later work. Table administration returns no QR secret. No universal development login, fictional cookie or environment identity switch is introduced.

Contracts precede implementation. Tables have versions and owner-only mutation. An open visit prevents table rename/deactivation. Reads and commands enforce business/branch permissions. Commands lock in the existing business→branch order, commit audit/outbox facts atomically, and retain the original response for exact-body retries even after later state changes. The order form includes a reviewed pricing fingerprint as well as the publication ID; concurrent price-policy changes require a reload. Live availability is checked on submission. Queues use bounded keyset pagination and explicit refresh, with preparation staff restricted to accepted/preparing/ready work.

The operational interface has a separate, prominently labelled fictional rehearsal. Rehearsal interactions change only browser memory and cannot call the private mutation APIs, grant access, create actual orders or mark money paid. The same presentation and command interface will be used by the real service screen once verified sessions are connected. Its rehearsal totals are illustrative; server/DB acceptance is verified independently with fictional PostgreSQL fixtures.

Changing tables or opening/ending another seating cannot silently move an unsent draft or its order note. An on-page review lets staff keep working or explicitly discard it. A newly opened seating starts with fresh order fields. Preparation has its own accepted-work screen rather than floor/bill controls. A future cashier worklist must retain unsettled bills from ended visits as well as current seating; the current floor queue is a service queue, not financial reconciliation.

Validation covers isolation, role boundaries, exact pricing/options, menu/policy conflicts, unpaid acceptance, additional rounds, forbidden transitions, cancellation permissions, closed visits, retries after state advancement, overlapping table/visit/order commands, restart durability and no private-token disclosure. Browser rehearsal and responsive checks do not establish authenticated HTTP, guest phones, settlement, background delivery, pilot acceptance or a production launch.
