# Interrupted command recovery

15 October 2026. Extend the existing guest order, payer report, staff service and cashier commands. Merchant OTP/sign-in stays closed. Local fixture and browser evidence must remain separate from live operations.

Persist an encrypted pending-command record before sending a supported mutation. Keep the original operation, target, request UUID and body unchanged. IndexedDB transactions allow one pending command per actor/branch/domain across tabs. Bind records to the identity resolved by the server and encrypt the body with AES-GCM using a key derived from the current session CSRF secret and that scope. Use a separately derived HMAC key for the body comparison tag, avoiding a stored plain hash that could expose guessed amounts or private text. Neither derived key is extractable or persisted. Never persist the encryption secret, cookies, dining/table/invitation/bill capabilities, session nonce, or access-code issuance results. Storage failure prevents sending a new supported mutation. Browser storage is best effort: eviction, unavailable storage, corruption or lost identity requires supervised reconciliation, never an invented failed/successful result.

After reload, display the saved attempt without automatically resending it. The current verified identity checks its original request key against the server. COMMITTED identifies the original resulting record and timestamp; refresh current operational state separately. NOT_RECORDED is a momentary observation, not evidence that a delayed request cannot still commit. Retrying uses the same saved key and body, current CSRF, and current authorization. A changed session encryption secret can leave the body unreadable; the original metadata can still be checked or canceled with current authority.

Cancellation is a distinct server action. Under the same branch lock as the original command, return COMMITTED if it won first, or create an immutable cancellation tombstone if no result exists. All original commands check cancellation inside workflow_request. A delayed original request then fails rather than committing after the user replaces it. Cancellation never reverses a committed order, receipt, allocation, claim, correction or refund. Acknowledge a confirmed result or cancellation before removing the local journal entry and allowing another command. If another tab removes an entry already observed by this page, recheck its original metadata with current server authority and acknowledge the returned outcome on this page too; a peer deletion alone is not proof of success or cancellation. Never silently discard uncertain financial actions, use a new retry key, repeat a bank transfer, or show a timeout as a failed payment.

Eight contract operations cover GET status and POST cancellation for guest visit order requests, payer bill transfer requests, staff branch service requests and staff branch cashier requests. Guest/payer entry resolves actual cookies and rechecks expiry/revocation after taking the branch lock. A payer still needs same-session bill authority, including after renewal. Staff status/cancellation is restricted to the original actor, business, branch, operation and current permissions; it never accepts a caller-provided identity. Results expose only state, request/target/result IDs and recorded time, not command bodies, access secrets or staff evidence. Cancellation is idempotent for the same descriptor, bounded to ten new tombstones per actor/branch/minute, and creates audit/outbox evidence without a financial event.

Supported service mutations are table create/edit, seating open/end, staff order and order transition. Supported cashier mutations are receipt recording/allocation, claim review, credits, bill finalization/closure and refund request/review/execution. Guest recovery covers order submission; payer recovery covers transfer reports. Credential entry/issuance, session start/pair/leave, catalog/preparation editing, unsent drafts, background delivery, device-to-device recovery and real merchant authentication remain separate. The existing service rehearsal still uses fictional page memory and resets on reload; actual persisted recovery is verified separately on disposable configured HTTP/database fixtures.

Required checks include lost responses before/after commit, original-key replay, cancellation versus both delayed and already-running commands, no cross-actor/visit/bill/branch access, permission/grant revocation, current-state versus original-result distinction, encryption/secret exclusion, reload and two-tab journal behavior, failed storage, changed encryption secret, corrupted payload, and PostgreSQL restart. No check may add a merchant login bypass or use a real bank/account.
