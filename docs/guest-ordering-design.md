# Guest association and own-order tracking

15 October 2026. Local implementation and fictional acceptance only. Merchant OTP and verified merchant sessions remain deferred; no real venue is activated. Extend the connected service rehearsal with guest A and guest B, using the same orders as floor, preparation and cashier.

A static table link starts an anonymous table-scoped session. It is not proof of presence, an invitation to the current visit, or authority to read other diners' orders or bills. An authorized staff member issues a separate five-minute visit invitation after confirming the seating. Invitations may join up to twenty sessions to that visit; rotating an invitation invalidates the old invitation without removing already joined guests. Ending the visit blocks new joining and ordering. Existing own orders remain readable until the twelve-hour session expires or is explicitly revoked. A new seating requires a new session; leaving a session deliberately gives up its order access.

The guest database login inherits only a new menu_guest_api role. It has no table access, staff permissions, runtime membership or ability to select a tenant/user/guest UUID. Narrow security-definer entry functions resolve a SHA-256 hash of the opaque cookie, then set transaction-local context and clear staff/payer context. Every operation rechecks expiry and revocation. The guest session cookie is HttpOnly, SameSite Strict, host-only, path / and Secure on production HTTPS. Mutation requires exact Origin, a session-bound CSRF token, bounded strict JSON and a UUID retry key. No private token is carried in a URL, localStorage, audit/outbox payload or saved command response. Guest-facing pages use no-store and no-referrer.

Staff table-link and visit-invitation issuance requires current permission and version. Tokens are derived with HMAC-SHA-256 from an explicitly configured 256-bit server key, purpose, trusted staff identity, resource and retry key. SQL stores hashes and immutable issuance metadata only. Exact retries reconstruct the original token without storing plaintext; replay after rotation reports the invitation/link inactive. Changing the server key requires coordinated reissuance; old issuance retries conflict rather than silently producing another token. Anonymous session creation additionally binds a fresh cryptographic 32-byte client start nonce. The nonce is held with the interrupted command, never stored in plaintext in SQL, and must be redacted from request-body logs. A known retry UUID and public table link cannot recover another session. Creation reconstructs a cookie on exact retry; it never silently replaces an active cookie. Tokens and CSRF secrets are never included in checked-in projections or reports.

Order commands require current publication and a reviewed pricing fingerprint, validate required options and live availability, and derive all totals in PostgreSQL. Submitted requests are awaiting staff acceptance and do not create accepted charges. Exact retries return the original response after later service changes; a separate read returns the current state. Unknown/other-session order IDs use the same unavailable response. Lists page only the current session's orders. Guests receive no staff transition controls, receipt/provider data, other diners' notes or combined bill authority.

Database guards bound session starts per table (120 per hour), joins per visit (20), and new order requests per session (10 per minute). They serialize with the branch and survive restarts. These are initial abuse/technical guards, not commercial limits; deployment still needs trusted proxy configuration, edge/IP protection and measured pilot tuning. Unknown public capabilities are not written into the rate table. No external services are called.

The browser rehearsal uses fictional memory only, resets on reload, and issues obviously fictional invitations. Guests can browse menu items before joining; ordering remains disabled. On narrow screens, saved-order tracking appears before the next-order composer. Real guest endpoint adapters are exercised against disposable PostgreSQL using actual token/cookie validation; no caller identity override is added. Production configuration, verified merchant access, table-link delivery/printing, a reachable HTTPS origin, independent devices, supervised reconciliation, receiving-account onboarding and field acceptance remain activation gates.


## Local verification and production configuration

`python3 scripts/check-guest-ordering.py` creates its own private socket-only PostgreSQL cluster, applies all migrations, creates separate limited logins and generates an ephemeral capability key. It exercises actual request handlers, twelve direct HTTP requests, an eight-request maintained Postman session/order workflow, overlapping connections and restart. Its temporary Postman files are private and removed; reporting/upload are disabled. Saved projections replace capabilities/CSRF with obvious fictional placeholders. `python3 scripts/check-guest-http.py` checks the unconfigured preview separately. The rehearsal at `/service/rehearsal` is memory only; `/visit` uses actual cookie-backed endpoints and starts without a seeded identity.

Live configuration eventually requires `MENU_GUEST_DATABASE_URL` for a login inheriting only `menu_guest_api`, `MENU_GUEST_CAPABILITY_KEY` holding a cryptographic 32-byte base64url key, a separately configured limited merchant connection, trusted verified staff sessions and an HTTPS deployment. The guest pool rejects superuser/BYPASSRLS/admin logins and memberships in runtime, identity, workflow-owner or platform roles. Fixture configuration accepts only development and the disposable test socket/login; it cannot create identity from a request header, UUID or environment flag. Database, proxy and application logs must redact request bodies, cookie/CSRF headers, start nonces and bound SQL parameters; do not enable parameter-value logging for capability operations. Production TLS verifies the server certificate.

Table access and invitations are currently explicit codes in the staff/guest screens. Real QR delivery/printing and private invitation handoff are still a product/field gate. The development preview deliberately removes ambient merchant/guest connection/key variables and cannot create real guest sessions. Only the disposable acceptance fixture configures them. The current browser has one active anonymous session per origin; another seating requires explicit leave and a new session. Independent browser profiles/devices need independent cookies.

Separate payer authorization and already-sent transfer reports now extend this foundation; see [payer-claims-design.md](payer-claims-design.md). Bill authority does not follow from ordering. The shared projection keeps private order instructions and other payers references out of the combined bill, and reports stay unverified until the cashier records actual credited funds.
