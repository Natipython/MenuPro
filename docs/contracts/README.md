The current workflow contract is `postman/specs/workflow-v2.openapi.yaml`, with 73 generated/normalized requests in `postman/collections/menu-workflow-v2`. It covers tables, visits, staff service, combined bills, canonical receipts, allocations, refunds and scoped plan/staff commands. MenuMini_1 has four functional public validation/menu HTTP operations, 17 guest/payer capability operations requiring explicit limited configuration, and 40 merchant boundaries that stay closed while verified identity is deferred. The other 12 operations remain target contracts. These routes are separate from the app/ reference prototype. See [workflow foundation](../workflow-foundation.md) for database support and remaining handler/replay work.

`postman/specs/openapi.yaml` and `menu-mini-v1` preserve the narrower initial order-linked contract. They are historical foundation examples, not the current bill-settlement design. Do not mix their payment paths with v2.

The local Postman collection includes saved examples and assertions for subsequent implementation. Do not treat example responses or a specification lint pass as live endpoint verification. Complete authenticated principal handling, server-side publication/price validation, and guest ownership checks before running the transaction flow against an application database.

Command retries retain their original dining session and idempotency key. A successful replay returns the original resource; using the key with a different canonical body returns 409. A changed publication/price or unavailable item requires customer confirmation, rather than a silent replacement or false order-success state.

Full Postman workspace governance is not part of the local syntax check and no cloud workspace is linked.

To rebuild v2 locally: run `python3 scripts/build-workflow-contract.py`, generate the collection with the pinned Postman CLI (`postman spec generate collection postman/specs/workflow-v2.openapi.yaml -n menu-workflow-v2 --force`), then run `python3 scripts/prepare-workflow-collection.py`. Check for stale generated requests when an operation summary is renamed; the contract checker rejects duplicates. Run `python3 scripts/check-menu-workflow-db.py` before `python3 scripts/check-workflow-contract.py` to validate actual database projections too. No live requests are sent by these scripts.

The guest fixture suite runs the maintained eight guest requests through a private temporary collection with fresh fictional capability values and a local HTTP origin. Cookie naming is adjusted only in that temporary local HTTP fixture. It does not add a merchant identity bypass, persist secrets in the maintained collection or upload a run. See [guest-ordering-validation.json](../guest-ordering-validation.json) and [guest-postman-validation.txt](../guest-postman-validation.txt).

The maintained five payer requests are executed separately against a disposable local fixture with both guest and bill cookies. Reports remain pending until the existing cashier independently records actual received funds and explicitly allocates them. See [payer-claims-validation.json](../payer-claims-validation.json), [payer-postman-validation.txt](../payer-postman-validation.txt) and the separate fictional browser evidence.

Eight recovery operations expose original-key status and cancellation for guest orders, payer reports, staff service and cashier commands. A status receipt carries no original command body or access secret. NOT_RECORDED does not authorize a replacement: explicitly retry unchanged or confirm serialized cancellation first. Four maintained guest/payer recovery requests execute against disposable cookie HTTP fixtures; staff HTTP remains closed. See [command-recovery-design.md](../command-recovery-design.md) and [command-recovery-validation.json](../command-recovery-validation.json).
